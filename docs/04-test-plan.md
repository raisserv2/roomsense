# RoomSense: test plan and test cases

The results of running this plan are in [05-test-report.md](05-test-report.md), which is generated by `python scripts/test_report.py`.

## 1. Scope

| In scope | Out of scope |
|---|---|
| The shared library (`roomsense/`), the pipeline scripts, the inference API, the capture service, the deployment configuration, the web UI, the end-to-end drift → retrain → recovery loop | Third-party tools themselves (MLflow, DVC, Ray, Prometheus, Grafana are assumed to work), load beyond one user, other rooms or cameras |

## 2. Test levels and tools

| Level | What it proves | How | Where it runs |
|---|---|---|---|
| **Unit** | Each function does what its contract says | `pytest`, no network, no GPU, no camera | Anywhere (Legion, any laptop) |
| **API (component)** | Each endpoint returns the specified output and error codes | `pytest` + FastAPI `TestClient` with a tiny generated ONNX model and a fake MLflow client | Anywhere |
| **Configuration** | Compose, Prometheus, alert rules, DVC and MLproject files are consistent with each other and with the design rules (loose coupling, localhost-only ports, every alert metric exists) | `pytest` reading the YAML/JSON | Anywhere |
| **Static** | PEP 8 style, import order, likely bugs | `ruff check .` | Anywhere |
| **Pipeline (integration)** | The six DVC stages run end to end and record themselves | `python scripts/run_pipeline.py`; success, cached and failing runs | Legion |
| **System (live)** | The deployed stack answers within limits | `python scripts/test_report.py --api <url>` | Legion → nova |
| **Acceptance / UI** | A person can use it; the loop closes | Manual cases in section 4.3, recorded in the demo video | Browser + room |

**Environment.** The tests need only `requirements-dev.txt` (ONNX Runtime, FastAPI, pytest, ruff). `mlflow run . -e test` builds the project environment from `python_env.yaml` and runs the same command inside it, so the test environment is identical to the development one.

**How to run.**

```bash
pytest                                   # the automated suite
ruff check .                             # style
python scripts/test_report.py            # both, plus acceptance criteria → docs/05-test-report.md
python scripts/test_report.py --api https://nova.tailb5cb87.ts.net:4443/api   # adds the live checks
```

**Entry criteria:** the branch installs and `dvc.yaml` parses. **Exit criteria:** every automated test passes and every acceptance criterion in section 5 is met.

## 3. Test data

- Unit and API tests generate their own data: flat-colour images, a 300-row synthetic manifest, a tiny ONNX model built in the test (`tests/conftest.py`). No private picture is needed to run the suite.
- The pipeline integration test was also run on a synthetic dataset (6 classes × 5 sessions × 24 frames) to check all stages, the cached path and a forced failure.
- System and acceptance tests use the real room.

## 5. Acceptance criteria

The software is accepted when all of these hold. Thresholds are in `params.yaml` (`acceptance:`), so they are versioned with the code. `scripts/test_report.py` measures AC-1 to AC-14 and writes the result into the test report; AC-15 to AC-17 are checked by hand (section 4.3) and shown in the demo video.

| ID | Criterion | Threshold | Why this number |
|---|---|---|---|
| AC-1 | Every automated test passes | 0 failures | Basic correctness |
| AC-2 | Code follows PEP 8 | 0 `ruff` violations | Standard Python coding style |
| AC-3 | Test macro-F1 of the latest trained model (ONNX) | ≥ 0.60 | Six classes: chance is about 0.17. 0.60 means the model is clearly useful while leaving room for the known hard pair (sitting vs lying on the bed) |
| AC-4 | One prediction on 2 CPU threads, p95 | ≤ 100 ms | A frame arrives every 5 s; 100 ms keeps nova's CPU almost idle |
| AC-5 | ONNX vs PyTorch outputs | max difference < 0.001 | What is served must be what was evaluated |
| AC-6 | No session shared between splits | enforced by test | No leakage |
| AC-7 | Every class present in validation and test | none missing | Otherwise the score says nothing about that class |
| AC-8 | Raw rows failing data quality checks | ≤ 5% | A snapshot with more is broken |
| AC-9 | Ray resize throughput | ≥ 100 frames/s | The full dataset (about 27 000 frames) preprocesses in minutes |
| AC-10 | API up and serving a model | yes | Live check |
| AC-11 | `POST /predict` p95, network included | ≤ 500 ms | Feels instant in the UI |
| AC-12 | Prometheus metrics exposed | yes | Live check |
| AC-13 | Pipeline console answers, MLflow reachable | yes | Live check |
| AC-14 | Latest pipeline run succeeded | yes | Live check |
| AC-15 | Drift alert fires after a lighting change | ≤ 10 min | TC-E2E-1 |
| AC-16 | Retrain restores a non-drifting state | share < 50%, alert resolved | TC-E2E-2 |
| AC-17 | A non-technical person can read the Live page | yes | TC-UI-9 |

### Result of the final run (14 Nov 2026)

13 of the 14 measured criteria are met (see [05-test-report.md](05-test-report.md)). **AC-3 is not met:** the final model (v5) scored 0.518 macro-F1 on its test split, below the 0.60 threshold. It was not promoted, and the champion remains v2.

The threshold was kept as defined rather than lowered after the fact. The miss reflects how small and unstable the test split is, not a regression in the code: the previous candidate (v3) scored 0.652 two days earlier on almost the same data. The split is recomputed whenever the dataset grows, and the classes other than `at_desk` have only 7 to 45 test frames each, so one session landing in a different split moves the score by about 0.1. The fix is a "sticky" split that keeps earlier session assignments, plus more sessions for the rare classes (see the HLD, section 5).

## 6. Defect handling

A failing test blocks the merge. Failures found in manual testing are fixed on a branch, a regression test is added where one can be automated, and the report is regenerated.
